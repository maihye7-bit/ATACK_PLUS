# ATACK PLUS — تصميم المزامنة (مراجعة Phase 1)

## 1. المبادئ الملزمة

1. **Offline-first:** SQLite هي قاعدة التشغيل المحلية، ويمكن تسجيل العمليات محلياً دون اتصال.
2. **Outbox دائم:** كل عملية لها `operation_id` ثابت (UUID) وبصمة payload ثابتة؛ لا يُنشأ UUID جديد عند إعادة المحاولة.
3. **Idempotency:** الخادم يسجل `(store_id, operation_id)` مع `payload_hash`. تكرار المفتاح والبصمة نفسها يعيد نتيجة العملية السابقة؛ المفتاح نفسه مع بصمة مختلفة يُرفض كتعارض أمني/بياني.
4. **المعاملة التجارية ذرية:** الفاتورة وعناصرها وحركة المخزون وقيد العميل/المورد والمدفوعات المرتبطة بها وحدة عمل واحدة على الخادم. لا تُرسل هذه السجلات كسلسلة RPC مستقلة وتفترض أنها ذرية.
5. **لا LWW للأموال أو المخزون:** لا تتم مزامنة `stock.quantity` أو أرصدة الديون عبر استبدال قيمة الصف من جهاز بآخر.
6. **لا فقد صامت:** عند التعارض تحفظ العمليتان والبيانات اللازمة للمراجعة، ولا تُحذف إحداهما تلقائياً.

## 2. الحفظ المحلي

تتم العملية محلياً داخل معاملة SQLite واحدة:

1. التحقق من الصلاحيات وحالة المنتج والعميل/المورد.
2. إنشاء سجل العملية التجارية ومعرفاتها UUID.
3. إنشاء العناصر وحركات المخزون وقيود الدفتر ذات الصلة.
4. إنشاء Outbox entry واحد يمثل العملية التجارية أو aggregate، ويحمل `operation_id` و`payload_hash`.
5. Commit ثم إظهار النجاح المحلي للمستخدم.

لا يُسمح بتحديث كمية المخزون أو رصيد الدين وحده دون حركة/قيد مصدره واضح.

## 3. Push إلى PostgreSQL

### 3.1 تسلسل العمل المستهدف

1. يقرأ Sync Engine عناصر Outbox حسب ترتيب الإنشاء/التبعيات.
2. يتحقق الخادم من هوية Supabase Auth وعضوية المتجر وصلاحية RBAC.
3. يتحقق من `operation_id` و`payload_hash`.
4. يطبق aggregate كاملاً داخل **RPC واحدة** ومعاملة PostgreSQL واحدة.
5. يسجل حركات المخزون والدفتر وAudit Log ويحدّث المجاميع المشتقة ضمن المعاملة نفسها.
6. يعيد نتيجة نهائية قابلة لإعادة الإرسال بأمان، ثم يعلّم الجهاز Outbox بأنه SYNCED.

### 3.2 حالة التنفيذ في مخطط Phase 1

- `processed_operations` و`atomic_process_operation` يقدمان أساس idempotency.
- `apply_outbox_operation` يسمح بمزامنة بعض بيانات التعريف/المرجعيات، ويتحقق من صلاحيات المجال.
- تم منع استخدام `apply_outbox_operation` العام للجداول التجارية المشتقة (الفواتير، المشتريات، المخزون، الديون، المدفوعات، المرتجعات، المصاريف والإيرادات). هذه تحتاج RPC تجارية ذرية مخصصة قبل تفعيل مزامنتها.
- لذلك لا تعتبر مزامنة جميع أنواع المعاملات مكتملة بعد. يجب إنشاء RPCs مثل `process_sale_aggregate`, `process_purchase_aggregate`, `process_customer_payment`, `process_supplier_payment`, `process_sales_return`, `process_stock_adjustment` واختبارها قبل ربطها بالتطبيق.

## 4. Pull و Change Log

### 4.1 Cursor لكل متجر

يستخدم PostgreSQL جدول `store_sync_counters` لتخصيص `sync_cursor` متزايد لكل متجر. تقوم `get_next_change_cursor(store_id)` بتحديث صف العداد داخل معاملة الكتابة؛ قفل الصف يبقى حتى Commit.

هذا يتجنب مشكلة `nextval()` التي قد تسمح لمعاملة متأخرة بالحصول على cursor أصغر ثم Commit بعد معاملة ذات cursor أكبر، وهو ما قد يؤدي إلى تخطي تغيير عند ACK.

المفتاح الفريد هو `(store_id, sync_cursor)`. لا تستخدم `change_log.id` كبديل عن cursor؛ `id` مجرد معرف تسلسلي تقني.

### 4.2 Pull

يقرأ الجهاز:

```sql
SELECT record_uuid, operation,
       CASE WHEN operation = 'DELETE' THEN old_values_json ELSE new_values_json END AS record_json,
       sync_cursor, created_at
FROM change_log
WHERE store_id = :store_id
  AND sync_cursor > :last_cursor
ORDER BY sync_cursor ASC
LIMIT 500;
```

يجب أن تكون القراءة عبر RPC آمنة تتحقق من:
- عضوية المستخدم في المتجر.
- أن الجهاز مسجل للمتجر ومربوط بحساب التطبيق المصادق نفسه.
- إثبات امتلاك اعتماد الجهاز السري، وليس مجرد معرفة `device_id`.
- أن cursor غير سالب.
- حدود pagination وإثبات التسليم (يستكمل في D3.2 / R3).

في D3.2 / R2 أضيف جدول خاص `device_credentials` يربط الجهاز والمتجر ومستخدم التطبيق. المالك الذي يملك `sync.manage` يسجل الجهاز للمستخدم المستهدف عبر `register_sync_device`، ويستطيع تدوير الاعتماد أو إبطاله عبر RPCs مخصصة. يُعاد رمز الجهاز الخام مرة واحدة فقط، ويُخزن الخادم بصمته SHA-256 دون تخزين الرمز نفسه. يجب على العميل حفظ الرمز في تخزين آمن وإرساله مع كل طلب مزامنة.

تستخدم التطبيقات المصادق عليها نسخ RPC المرتبطة باعتماد الجهاز. بعد D3.2 / R3 أصبح عقد Pull/ACK كالتالي:
- `get_unsynced_records_page(store_id, device_id, table_name, device_token)` يعيد `delivery_id` و`events` و`event_count` و`has_more`.
- `acknowledge_sync_cursor(store_id, device_id, table_name, delivery_id, device_token)` يقر صفحة سبق أن أصدرها الخادم؛ لا يرسل العميل Cursor اعتباطياً.
- `create_outbox_entry(..., device_token)`
- `apply_outbox_operation(outbox_id, device_id, device_token)`

تم إلغاء صلاحية استدعاء نسخ Pull/ACK القديمة التي لا تتضمن إثبات التسليم من دور `authenticated`، وكذلك نسخة Pull/ACK التي تتضمن اعتماد الجهاز فقط دون Delivery ID. تبقى النسخ القديمة لمسارات `service_role` الموثوقة. الأجهزة القديمة غير المرتبطة باعتماد تحتاج إلى إعادة تسجيل من المالك قبل استخدام مسارات المزامنة المصادق عليها.

يُنشئ الخادم سجل `sync_delivery_pages` لكل صفحة تحتوي أحداثاً مرئية، ويربطه بالمتجر والجهاز والجدول وحدود Cursor وبصمة الصفحة وإصدار اعتماد الجهاز. تكرار Pull قبل ACK يعيد هوية الصفحة نفسها إذا لم تتغير محتوياتها. لا يقبل ACK إلا Delivery ID المسجل للجهاز والصفحة الحالية، وبالترتيب الصحيح؛ ويكون ACK المكرر idempotent.

تُحسب `has_more` على الأحداث المسموح بها للمستخدم فقط. إذا لم توجد أحداث مرئية، يتقدم الخادم داخلياً عبر نطاق الأحداث غير المصرح بها دون كشف عددها أو هويتها أو إظهار Delivery ID. ولا يعرض عقد الصفحة أرقام Cursor الداخلية للعميل.

### 4.3 ACK

- على العميل تطبيق أحداث الصفحة محلياً داخل معاملة واحدة، وتخزين Delivery ID، ثم إرسال ACK بعد نجاح Commit.
- الخادم يثبت أن الصفحة صادرة منه ومخصصة للجهاز، لكنه لا يستطيع إثبات أن العميل نفذ Commit محلياً؛ هذه مسؤولية عقد العميل واختباراته.
- لا يتقدم Cursor عند فشل تطبيق أي سجل في الصفحة.
- لا يقبل الخادم ACK لصفحة غير مسجلة أو لجهاز آخر أو لصفحة لاحقة قبل السابقة.
- يبقى تقدم كل جهاز مستقلاً.
- لا يحذف الخادم change_log أو tombstones أو سجلات Delivery بناء على مدة زمنية فقط؛ سياسة الاحتفاظ والتنظيف تحتاج قراراً واختبارات منفصلة.

### 4.4 عقد Tombstone وهوية الحذف

Tombstone INSERT هو إشارة الحذف الأساسية. تحديث السجل الأصلي إلى `is_active=false` حالة متوافقة، وليس إشارة حذف مستقلة. يسجل المسار الحالي Tombstone أولاً ثم تحديث السجل الأصلي؛ لذلك قد يصل حدث Tombstone قبل UPDATE الخاص بالسجل.

يعيد Pull في stream `tombstones` غلاف DELETE موحداً:
- `event_type = DELETE` و`operation = DELETE`.
- `table_name` و`record_uuid` يحددان الكيان الأصلي.
- `tombstone_id` يحدد صف Tombstone، وهو مستقل عن `record_uuid`.
- `store_id` و`deleted_at` و`deleted_by` جزء من الغلاف.
- تحديثات metadata أو الحذف الفيزيائي لصف Tombstone لا تُرسل كإشارات حذف جديدة؛ Tombstone INSERT هو الحدث المعتمد.

الهوية المنطقية هي `store_id + table_name + record_uuid`. الجداول الخمسة القابلة للحذف الناعم تستخدم UUID عالميّاً كمفتاح أساسي؛ لذلك يبقى قيد قاعدة البيانات الأقوى `UNIQUE(table_name, record_uuid)` دون إضافة `store_id`. إذا تغيرت دلالات المفاتيح الأساسية مستقبلاً، يجب إعادة تقييم القيد.

على العميل حفظ علامة الحذف بهذه الهوية، مع الاحتفاظ بـ`tombstone_id` منفصلاً. إذا لم يكن السجل المحلي موجوداً، يحتفظ العميل بعلامة الحذف حتى لا يعيد إدخال نسخة قديمة. وإذا كان موجوداً، يخفيه من العرض النشط. أي UPDATE أقدم يصل بعد Tombstone لا يجوز أن يعيد تنشيط السجل. تكرار الحدث يجب أن يكون idempotent.

حقلا `tombstones.sync_status` و`tombstones.synced_at` محفوظان للتوافق التاريخي فقط، ولا يمثلان حالة جميع الأجهزة. لا يغيّر ACK الخاص بجهاز واحد هذين الحقلين. التقدم المعتمد لكل جهاز محفوظ في `sync_cursors`، وإثبات ACK لكل صفحة في `sync_delivery_pages`. كما أن `sync_delivery_pages.acknowledged_at` يثبت إقرار الصفحة من الجهاز، وليس نجاح Commit المحلي الذي يجب على العميل ضمانه.

### 4.5 Pagination وترتيب الصفحات

- الحد الأقصى للصفحة هو 500 حدث مرئي.
- لا يرسل العميل Cursor يختاره؛ الخادم يقرأ آخر Cursor معتمد للجهاز والجدول.
- يجب تطبيق الصفحة محلياً داخل معاملة واحدة ثم ACK باستخدام Delivery ID، وبعدها فقط يطلب العميل الصفحة التالية.
- `has_more` يعبّر عن وجود أحداث أخرى مرئية للمستخدم، ولا يكشف عدد أو وجود أحداث مخفية.
- إذا لم توجد أحداث مرئية، يتقدم الخادم عبر النطاق غير المرئي داخلياً ويعيد استجابة فارغة بلا Delivery ID.
- إعادة Pull قبل ACK تعيد الصفحة نفسها ما دامت محتوياتها وبياناتها الوصفية لم تتغير.
- يقفل Pull وACK صف `sync_cursors` للجهاز/الجدول بترتيب موحد بعد التحقق من اعتماد الجهاز؛ وهذا يمنع تقدم الصفحات خارج الترتيب.
- الأحداث التي تُكتب بعد لقطة الصفحة الحالية تبقى للصفحة التالية بعد ACK، ولا تُضم إلى صفحة سبق إصدارها.
- تبقى الجداول Streams مستقلة. لا نحتاج Global Stream حالياً؛ Tombstone هو إشارة الحذف المعتمدة ويجب أن تتغلب على UPDATE قديم يصل من Stream آخر.

## 5. التعامل مع تعدد الأجهزة والمخزون

عند العمل دون اتصال لا يمكن ضمان منع جهازين من بيع آخر وحدة مشتركة لحظياً إذا كان كلاهما يملك نسخة محلية قديمة.

الحلول الممكنة:
- حجز حصص مخزون مسبقاً لكل جهاز/موقع عند توفر الاتصال؛ أو
- قبول تسجيل العمليات محلياً ثم إجراء تحقق مركزي عند المزامنة، وإظهار عجز/تعارض صريح للمدير دون حذف الفاتورة أو اختلاق كمية.

لا يتم دمج رصيد المخزون بجمع قيم `quantity` المحلية. الدمج يكون من خلال أحداث بيع/شراء/مرتجع/تسوية فريدة ومتحقق منها.

## 6. Tombstones و Full Sync

- كل حذف متزامن يحتاج tombstone بمعرف السجل والمتجر ونوع الجدول ووقت الحذف وهوية المنفذ.
- لا تُحذف tombstones بعد 30 يوماً بشكل أعمى.
- عند جهاز جديد أو cursor أقدم من فترة الاحتفاظ، يطلب Full Sync موثقاً.
- Full Sync يجب أن يستخدم snapshot متسقاً أو آلية مزامنة تمنع الفجوات أثناء استمرار الكتابة.
- شرط مثل `last_sync_seq > MAX(change_log.id) - 30_days` غير صحيح؛ ID sequence ليس مدة زمنية.

## 7. حالات Outbox

`PENDING → IN_PROGRESS → SYNCED`

وعند الخطأ:
- خطأ قابل لإعادة المحاولة: `FAILED` مع retry/backoff.
- تعارض بيانات: `CONFLICT` مع حفظ التفاصيل.
- لا تحول العملية إلى `SYNCED` إلا بعد تأكيد الخادم أن المعاملة التجارية اكتملت.

## 8. اختبارات قبول المزامنة

1. إعادة إرسال نفس operation_id وpayload عشر مرات لا يكرر الأثر.
2. نفس operation_id مع payload مختلف يُرفض.
3. انقطاع الاتصال قبل ACK ثم إعادة الإرسال لا يكرر البيع أو الدفع.
4. فشل عنصر من aggregate يؤدي إلى Rollback كامل.
5. معاملتان متزامنتان في متجر واحد لا تنتجان cursor مفقوداً.
6. أجهزة متجر آخر لا تستطيع Pull أو Push بيانات هذا المتجر.
7. جهاز غير مسجل لا يستطيع Pull.
8. حذف ثم Pull يطبق tombstone بالترتيب.
9. بيع آخر كمية من جهازين Offline ينتج حالة تعارض/عجز واضحة ولا يكتب فوق حركة الجهاز الآخر.
10. لا يمكن تحديث stock أو ledger أو payment عبر generic row sync.

## 9. حدود التنفيذ الحالية

هذه الوثيقة تصف التصميم بعد تصحيح نقاط الخطر، ولا تثبت أن Flutter Sync Engine أو RPCs التجارية قد نُفذت. يجب اعتبار مزامنة العمليات التجارية غير جاهزة للإنتاج حتى تنفذ RPCs الذرية واختبارات PostgreSQL الحقيقية.


# Phase 2 — تنفيذ RPCs التجارية الذرّية

تمت إضافة ملف ترحيل مستقل `ATACK_PLUS_PHASE2_BUSINESS_RPCS.sql` يُطبق بعد مخطط المرحلة الأولى. لا تُرسل صفوف الفاتورة وعناصرها وحركات المخزون كعمليات Outbox منفصلة؛ يرسل العميل payload عملية واحدة إلى RPC واحدة.

## RPCs المتاحة في هذه المرحلة

- `process_sale_invoice(p_store_id, p_operation_id, p_payload)`: فاتورة البيع + العناصر + خصم المخزون + حركات المخزون + قيد العميل + دفعة البيع الاختيارية وتخصيصها.
- `process_purchase(...)`: فاتورة الشراء + العناصر + إضافة المخزون + حركات المخزون + قيد المورد + دفعة المورد الاختيارية.
- `process_customer_payment(...)`: دفعة العميل + دفتر العميل + تخصيصات الفواتير + تحديث المتبقي. يُخصص الجزء غير المحدد تلقائياً على أقدم الفواتير المستحقة (FIFO)، ولا يسمح بترك مبلغ غير مخصص في هذا الإصدار أو دفع أكبر من الدين القائم.
- `process_supplier_payment(...)`: دفعة المورد + دفتر المورد + تحديث الدين.

## عقد payload

كل عملية تتطلب `id` UUID ثابتاً للكيان، و`p_operation_id` UUID ثابتاً للعملية. يعاد إرسال نفس الاثنين مع نفس payload عند انقطاع الاتصال. يعاد رد `replayed=true` عند التكرار المطابق، ويرفض الخادم operation_id إذا تغير payload.

- البيع: `id`, `invoice_number`, `customer_id` اختياري، `invoice_date`, `due_date`, `location_id`, `paid_amount`, `payment_method`, `notes`, و`items[]`. كل عنصر: `id?`, `product_id`, `quantity`, `unit_id`, `unit_price`, `discount_amount?`, `tax_rate?`, `batch_number?`, `expiry_date?`.
- الشراء: `id`, `purchase_number`, `supplier_id`, `purchase_date`, `location_id`, `paid_amount`, `payment_method`, `notes`, و`items[]`. كل عنصر: `id?`, `product_id`, `quantity`, `unit_id`, `unit_price`, `cost_per_unit?`, `tax_rate?`, `batch_number?`, `expiry_date?`.
- دفعة العميل: `id`, `customer_id`, `amount`, `payment_method`, `reference_no?`, `notes?`, `allocations?:[{invoice_id,amount}]`. يطبق الخادم التخصيصات المحددة أولاً ثم يوزع المتبقي FIFO على أقدم الفواتير المستحقة؛ يجب تخصيص كامل الدفعة، ولا يسمح برصيد غير مخصص في هذا الإصدار.
- دفعة المورد: `id`, `supplier_id`, `amount`, `payment_method`, `reference_no?`, `notes?`.

الخادم يحسب إجماليات السطور والضرائب ويحوّل الكمية إلى الوحدة الأساسية باستخدام `product_units.conversion_factor`؛ لا يثق بإجماليات مرسلة من العميل. كل تحديثات الرصيد والحركة ضمن المعاملة نفسها.

## ما لم يدخل بعد

المرتجعات، المصاريف/الإيرادات، الاستلام الجزئي للمشتريات، التحويلات بين المخازن، الحجوزات، والدفعات المقدمة التي تتجاوز الدين القائم تحتاج RPCs مستقلة في مرحلة لاحقة. لا تستخدم generic sync لتجاوز ذلك.
