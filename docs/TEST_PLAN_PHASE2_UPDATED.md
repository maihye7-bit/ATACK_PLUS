# ATACK PLUS — خطة الاختبار (Phase 1)

## 1. حالة الدليل والاختبارات

هذه خطة اختبارات، وليست تقرير نجاح. يجب تسجيل كل اختبار مع البيئة، الأمر المنفذ، النتيجة الفعلية، وسجل الخطأ عند الفشل. لا تضع PASS قبل تشغيل الاختبار.

| الطبقة | الأداة/البيئة | ما تثبته |
|---|---|---|
| SQLite Schema | SQLite 3 حديث + `PRAGMA foreign_keys=ON` | إنشاء الجداول والفهارس والمشغلات وقيود FK |
| PostgreSQL Schema | PostgreSQL 15+ أو Supabase staging | صحة DDL وPL/pgSQL والسياسات والدوال فعلياً |
| RLS | حسابا Auth على الأقل + متجران | العزل والصلاحيات حسب المستخدم والدور |
| Flutter | `flutter test` و`flutter analyze` | منطق التطبيق والـ repositories والـ sync engine |
| Android | Emulator وجهاز فعلي | تشغيل الهاتف والباركود والطباعة والعمل Offline |
| Windows | Windows 10/11 | البناء والطباعة وقاعدة SQLite والتزامن |
| Multi-device | جهازان أو أكثر | التعارضات والمزامنة بعد الانقطاع |

## 2. اختبارات المخطط المحلي SQLite

- نفذ كل كتل SQL بالترتيب كما وردت في `SQLITE_SCHEMA_PHASE1_FIXED.md`.
- تحقق من `PRAGMA foreign_keys = ON` لكل اتصال.
- نفذ `PRAGMA foreign_key_check` ويجب أن يرجع صفراً.
- تحقق من وجود جميع الجداول والفهارس والمشغلات المتوقعة.
- اختبر uniqueness لكل متجر: يمكن تكرار code/barcode/رقم الفاتورة في متجر آخر، ولا يمكن تكراره داخل المتجر نفسه.
- اختبر منع المراجع العابرة للمتاجر.
- اختبر `SUPPLIER_DEBT` في `sync_conflicts`.
- اختبر tombstone وتاريخ الإنشاء والحذف.

## 3. اختبارات PostgreSQL الفعلية

لا يكفي فحص SQL نصياً. شغّل المخطط على قاعدة فارغة PostgreSQL 15+، مع توفر Supabase Auth schema/functions عند اختبار دوال `auth.uid()` و`auth.role()`.

### 3.1 إنشاء المخطط

1. نفّذ الملف كاملاً باستخدام `psql -v ON_ERROR_STOP=1` أو Supabase migration pipeline.
2. يجب أن ينتهي التنفيذ برمز خروج 0.
3. افحص `pg_tables`, `pg_indexes`, `pg_trigger`, `pg_policies`.
4. تحقق من أن `invoice_items` عليه RLS وسياسات SELECT/INSERT/UPDATE/DELETE.
5. تحقق من وجود الفهارس المركبة لكل معرف تجاري داخل المتجر.
6. تحقق من `store_sync_counters` و`UNIQUE(store_id, sync_cursor)`.

### 3.2 RLS وRBAC

أنشئ متجرين A وB، ومستخدمين منفصلين لكل متجر، وأدواراً مختلفة. اختبر SELECT/INSERT/UPDATE/DELETE على كل جدول حساس.

- مستخدم A لا يقرأ أو يعدل بيانات B.
- `cashier` لا ينفذ عمليات لا تسمح بها صلاحياته.
- مستخدم بلا `sales.write` لا ينشئ فاتورة.
- مستخدم بلا `users.manage` لا يعدل الأدوار أو سجلات المستخدمين، حتى عبر PostgREST مباشرة.
- مستخدم بلا صلاحية المجال لا يكتب مباشرة إلى المنتجات/العملاء/الموردين.
- الجداول المالية والمخزنية وجداول المزامنة لا تقبل كتابة REST مباشرة من `authenticated`؛ الكتابة تتم عبر RPC موثوقة فقط.
- المستخدم الأول للمتجر يحصل على `owner` ضمن معاملة إنشاء المتجر.
- لا تعتبر اختبار `service_role` اختباراً لـ RLS؛ هذه الصلاحية تتجاوز السياسات.

### 3.3 Idempotency

- نفس `(store_id, operation_id, payload_hash)` يعاد دون أثر مكرر.
- نفس `(store_id, operation_id)` مع hash مختلف يرفض.
- عمليتان متزامنتان بنفس operation_id تنتجان أثراً واحداً فقط.

### 3.4 Cursor وترتيب التغييرات

نفذ اختبار تزامن بمعاملتين على المتجر نفسه:
1. المعاملة A تخصص cursor ثم تتأخر قبل Commit.
2. المعاملة B تحاول تسجيل تغيير آخر.
3. تحقق أن B تنتظر قفل عداد المتجر، ولا تستطيع Commit بتسلسل أعلى قبل A.
4. بعد Commit، يجب أن يكون كل cursor ضمن التسلسل متاحاً عبر Pull.

نفذ أيضاً اختباراً لمتجرين مختلفين للتأكد من استقلال العدادين.

## 4. اختبارات سلامة العمليات التجارية

هذه الاختبارات لا تصبح قابلة للنجاح حتى تُنفذ RPCs الذرية المتخصصة:

- فاتورة بيع + عناصر + حركة مخزون + قيد عميل في معاملة واحدة.
- شراء + عناصر + حركة مخزون + قيد مورد في معاملة واحدة.
- دفعة عميل + تخصيصات + تحديث دفتر العميل والفاتورة في معاملة واحدة.
- دفعة مورد + تحديث دفتر المورد في معاملة واحدة.
- مرتجع + عكس/إضافة حركة المخزون + قيد مالي في معاملة واحدة.
- فشل أي خطوة يعيد Rollback لجميع آثار العملية.
- generic `apply_outbox_operation` يرفض جداول المعاملات والمخزون والديون.

## 5. اختبارات المزامنة

1. Push لعملية واحدة ثم إعادة إرسالها 10 مرات.
2. نفس operation_id مع payload مختلف.
3. انقطاع الشبكة بعد نجاح الخادم وقبل ACK.
4. إغلاق التطبيق بعد معالجة جزء من صفحة Pull.
5. تطبيق صفحة Pull محلياً داخل معاملة واحدة ثم تحديث cursor.
6. جهاز غير مسجل يحاول Pull أو ACK.
7. جهاز من متجر A يحاول Pull أو ACK من متجر B.
8. ACK لا يتجاوز أعلى cursor موجود، ولا ينخفض عن ACK سابق.
9. حذف مع tombstone ثم جهاز يعود بعد مدة طويلة.
10. Full Sync أثناء استمرار إدخال عمليات جديدة.
11. فشل عملية داخل aggregate وعدم ظهور أي جزء منها في الخادم.

## 6. اختبارات المخزون والديون متعددة الأجهزة

- بيع آخر وحدة من جهازين Offline.
- مرتجعان متزامنان لنفس المنتج.
- تسديدان مختلفان للعميل نفسه.
- إعادة إرسال تسديد واحد بنفس operation_id.
- تخصيص دفعة لفاتورة عميل آخر.
- محاولة تعديل رصيد stock أو current_debt مباشرة.

النتيجة المطلوبة: لا مخزون سالب غير مصرح به، ولا تكرار قيود، ولا فقد عمليات، ولا LWW على الرصيد. إذا لم تُستخدم حصص مخزون مسبقة، يجب إظهار عجز/تعارض صريح عند المزامنة.

## 7. اختبارات تطبيق Flutter

الأوامر المطلوبة بعد تجهيز بيئة Flutter:

```bash
flutter pub get
flutter analyze
flutter test --reporter expanded
flutter build apk --release
flutter build windows --release
```

لا تسجل نجاح بناء Android أو Windows إلا بعد تشغيل الأوامر فعلياً على البيئة المستهدفة. اختبر RTL، DZD، أحجام الهاتف واللوحي، الطباعة الحرارية وPDF والباركود.

## 9. معايير قبول الإنتاج

- لا توجد أخطاء DDL أو PL/pgSQL في PostgreSQL 15+.
- جميع جداول البيانات الحساسة محمية بـ RLS وسياسات مختبرة.
- اختبارات الصلاحيات والعزل كلها ناجحة.
- العمليات التجارية ذرية وتُختبر بالفشل والنجاح.
- Idempotency وcursor وFull Sync مجربة تحت التزامن والانقطاع.
- لا توجد خسارة أو مضاعفة في المخزون والديون والمدفوعات.
- Flutter analyze/tests وAndroid/Windows builds ناجحة.
- النسخ الاحتياطي والاستعادة مجربان فعلياً.

**الحالة الحالية:** PostgreSQL لم يُشغّل بعد على خادم فعلي في بيئة هذه المراجعة؛ لذلك تبقى اختبارات PostgreSQL وRLS وFlutter وAndroid وWindows بحالة `NOT RUN` حتى تنفيذها.


# Phase 2 — اختبارات RPCs التجارية

تضاف الاختبارات التالية إلى PostgreSQL staging (لا تعتبر ناجحة قبل تشغيلها فعلياً):

| ID | الحالة | النتيجة المطلوبة |
|---|---|---|
| RPC-SALE-01 | بيع نقدي كامل | فاتورة وعناصر وحركات OUT وقيود متطابقة ضمن معاملة واحدة |
| RPC-SALE-02 | بيع آجل لعميل | زيادة الدين بالمتبقي فقط، مع قيد SALE بالقيمة الإجمالية |
| RPC-SALE-03 | بيع بكمية غير متاحة | Rollback كامل؛ لا فاتورة ولا حركة ولا قيد |
| RPC-SALE-04 | وحدة كرتون بمعامل 12 | تخفيض المخزون 12 وحدة أساسية لكل كرتون |
| RPC-SALE-05 | إعادة نفس operation_id والpayload | لا تتكرر الفاتورة أو الحركة؛ replay=true |
| RPC-SALE-06 | نفس operation_id مع payload مختلف | رفض صريح |
| RPC-PUR-01 | شراء نقدي/جزئي | زيادة المخزون وتسجيل إجمالي المورد والمدفوع والمتبقي بصورة صحيحة |
| RPC-PUR-02 | تكلفة وحدة غير أساسية | تخزين cost_price وتكلفة الحركة على أساس الوحدة الأساسية |
| RPC-CUSTPAY-01 | تسديد مع تخصيص لفاتورة | انخفاض الدين والمتبقي بالقيمة نفسها |
| RPC-CUSTPAY-02 | تخصيص لفاتورة عميل آخر | رفض وRollback |
| RPC-CUSTPAY-03 | تخصيص أكبر من المتبقي | رفض وRollback |
| RPC-CUSTPAY-04 | دفعة موزعة على عدة فواتير | التخصيصات الصريحة أولاً ثم FIFO، دون مبلغ غير مخصص |
| RPC-SUPPAY-01 | تسديد مورد ضمن الدين | خفض الدين وإضافة قيد PAYMENT |
| RPC-AUTH-01 | مستخدم بلا صلاحية العملية | رفض 42501 |
| RPC-TX-01 | إحداث خطأ بعد إنشاء الفاتورة وقبل نهاية العملية | لا يبقى أي جزء من العملية |
| RPC-CONC-01 | بيعان متزامنان على آخر كمية | لا يصبح stock.quantity سالباً ولا يكتمل إلا البيع المسموح |

## فحص ثابت أُجري على ملف المرحلة الثانية

- تأكيد وجود RPCs الأربعة، وفحص الصلاحيات وidempotency، وتحديث المخزون/الدفاتر داخل نفس أجسام الدوال.
- لا توجد بيئة PostgreSQL متاحة هنا؛ لم يُنفذ DDL أو PL/pgSQL على خادم. جميع حالات الجدول أعلاه حالتها `NOT RUN` إلى أن تنفذ على PostgreSQL 15+/Supabase staging.
